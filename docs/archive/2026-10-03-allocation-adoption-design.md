# Atomic adoption of reviewed allocation lines

## Problem and intended increment

The reviewed intake path now retains exact source partitions, assignments, fields, context, balanced allocation and explicit treatment. None creates a cost. The legacy confirmation service expects one active `invoice_document` per cost and releases that document after verifying its storage bytes. Its primary pointer cannot represent multiple costs from one source. Simply creating manual costs or calling legacy confirmation independently would bypass source evidence or permit a partial financial effect.

Implement a narrow atomic adapter for one whole-original logical document in one whole-property WEG/MIET scope. Require the latest treatment/allocation/context/field/assignment/partition/extraction bases, unchanged property/scope/category snapshots, explicit confirmation and whole-original disclosure acknowledgement, original custody preparation and current original export permission, destination prepare/confirm and current property authority. Only supported operating-expense, gross-without-input-VAT, marker-free treatment is eligible. Unknown invoice VAT remains unknown. No unresolved choice maps to a legacy billable flag. Reserve, capitalization, input-VAT claims and keys needing missing recipient/consumption evidence remain blocked. Broader methods still require the plan's specialist release evidence.

## Typed source bridge and complete financial set

An immutable allocation set pins the exact treatment, allocation, field review and original. One immutable primary link binds every exact allocation line to exactly one resulting cost. Deferred constraints seal membership and exact source/category/amount/treatment correspondence. Signed gross/VAT and tenant amounts are copied without rounding. The owner perspective remains the full gross, independently of the tenant share.

Create one typed, immutable intake-to-legacy-invoice bridge using the original's exact storage URI/backend/version/hash/size, without copying bytes. The legacy invoice's primary cost pointer is a deterministic compatibility pointer to the first allocation line, not an additional charge. The new complete link set is authoritative for all split-cost source readers. Repository source lookup, privacy retention queries and any corresponding SQL projections must account for every link. Retain the existing unique-primary constraint. The adapter must forbid an extra full-amount cost, replacement attachment or standalone correction from bypassing the allocation set; grouped corrections need a later explicit atomic contract.

The bridge is a deliberate publication under the destination accounting scope, governed by existing invoice-source access and export rules. Original intake and batch custody, and their private proposal/review histories, remain unchanged. Publish no private extraction payload, reason or documentary-basis notes in the legacy invoice extraction payload. An adoption receipt exposes approved cost/source facts only; granting cost access does not silently grant private intake notes. A new source pointer is not a new upload: any exception to the fresh-upload guard must require the typed exact bridge, not a fabricated upload admission. Released original fields remain unchanged. Migration backfill may create one-cost legacy sets only for proven same-organization links; it must not reinterpret unresolved old documents.

## Transaction and integrity boundary

The API verifies the current original bytes, size and hash read by URI against recorded storage identity. The existing store has no version-addressed read API: retain its version metadata but do not claim that a named object version or future byte immutability was verified. A private trusted-runtime attestation binds that result to the actor, exact command digest, source, request and caller transaction ID/backend PID. Ordinary SQL cannot forge or reuse it in another transaction. Its issuer must not wait for the caller's ACL/financial locks, following the existing separated-runtime admission pattern. The actual interactive database command rechecks current authority and freshness under ACL then financial serialization before consuming the attestation and producing any financial effect.

In one transaction create the allocation set, all costs and exact scope bindings, the complete source links, typed bridge, release/retention evidence and audit events. Any failed child/source/audit insert rolls everything back. Historical retry reauthorizes before returning the exact retained result and does not re-run storage or metadata freshness for a committed receipt. New calls cannot bypass confirmation by directly creating costs or releasing a bridge. No individual line becomes confirmed while another line fails.

## Duplicate gate and readiness

An absent visible candidate list does not establish uniqueness. Under the same serialization as ingestion/reviews/legacy source writes, derive a private preview digest from all relevant matching current review heads, retained adopted identity evidence, same-byte intake originals (including unprocessed receipts) and legacy source/cost evidence. The public preview returns generic blocking status without inaccessible IDs, names or counts. A changed digest invalidates a new adoption request.

A raw same-byte receipt without the exact required review/comparison blocks readiness. With reviewed identical sources, an explicit same-document comparison may select the first financial adoption; retained source claims then prevent a second charge from any copy. Business collisions require the exact current pair's distinct-document verdict; replacement intent never authorizes a new independent charge. Retained adopted identities cannot be erased by a later unrelated review. Cross-scope or legacy collisions lacking a supported typed comparison remain blocked. Raw unrelated receipts do not establish a known identity collision, but future review/adoption must still compare against retained adopted claims. Legacy confirmation of a reuploaded adopted source must use the same private duplicate guard. Inaccessible unresolved collisions produce only a generic conflict.

## Qualification before acceptance

Exercise positive invoices and negative credits; full/partial/zero tenant shares; unknown VAT; current confirm and original/property/scope revocation; pause and actual roles; forged, expired or cross-transaction attestation; concurrent predecessor/adoption and duplicate races; stale heads/snapshots/private candidate digests; unprocessed same-byte and inaccessible collisions; retained identity after review mutation; old and new entry-point double charge prevention; split child/audit/source failure rollback; exact committed replay; bridge metadata/FKs/sealing/immutability; no disclosure before commit; scope/export denial after commit; every split-cost source and privacy reader; guarded migration backfill/downgrade. Browser qualification must explicitly show resulting costs/source and test a lost committed response, denied confirmation and mobile rendering.

Independent read-only architecture review accepted the typed bridge approach subject to the source-export, complete-member, narrow-projection, downstream-mapping and storage-guarantee constraints incorporated above. The qualified increment below does not accept B3, cross-scope allocation, publication of partial-page extracts, grouped corrections or professional release gates.


## Implemented boundary and review repairs

Migration 0109 implements the narrow whole-original adapter, its private URI/hash/size attestation, sealed allocation sets and published links. The existing compatibility pointer still points to the first charge only. Source repositories and the SQL privacy-retention projection follow every member. Individual corrections return a deliberate conflict before creating a draft; database guards protect every member and source independently of API entry point. A logical-source result lookup requires current intake custody and destination source access, and returns only the published receipt.

Independent static review identified two defects before acceptance: attachment-based legacy duplicate discovery missed already confirmed manual costs without documents, and invoice dates after year 9991 produced retention dates outside Python's supported range. Both were repaired with targeted tests. A separate raw-receipt check was corrected to include originals before a registry reference exists. Legacy duplicate checks remain conservative when typed comparison evidence is unavailable. The second independent review found no further actionable blocker in the repaired backend and UI increment.
